1. The idea

Mutation testing: break the app on purpose in one small way, run the tests, see if anything fails. If nothing fails, the tests are blind to that bug. Bugsy does this on AI-written Kane CLI browser tests, then closes each gap with a test Kane designs from the requirement that was never written.

3. One experiment

sequenceDiagram participant B as bugsy run participant A as Ledger participant P as probe (HTTP) participant K as Kane CLI participant E as evidence pack B->>A: start BUG=none B->>K: run suite (baseline) K-->>E: all passed B->>A: stop, restart BUG=leak_cross_tenant B->>P: as Alice, GET /invoices/4 P-->>B: 200 and the page contains "Umbrella" (bug is live) B->>K: run the same suite, healing off K-->>E: all passed B->>E: read per-test status B-->>B: verdict = survived (green on a leaking app)

The probe proves the bug is really there before a Kane run is spent. Mutants run one at a time; the app restarts with fresh data before each, so tests never share state.

4. How a verdict is decided

flowchart TD S([Kane run finished]) --> Q1{Probe showed the bug is live?} Q1 -->|no| INV[invalid] Q1 -->|yes| Q2{Any test broken or interrupted?} Q2 -->|yes| INC[inconclusive] Q2 -->|no| Q3{Any test failed?} Q3 -->|no| SUR[survived] Q3 -->|yes| Q4{Failed after step 1, i.e. after reaching the app?} Q4 -->|no| INC Q4 -->|yes| Q5{Same test passed on the clean baseline?} Q5 -->|no| INC Q5 -->|yes| CAU[caught]

Catch rate = caught ÷ (caught + survived), over valid and conclusive experiments only. The report always shows inconclusive and invalid counts beside it. Verdicts come from Kane's per-test status and failing step in the evidence pack, never from the exit code alone.

5. The fix loop

sequenceDiagram participant U as You participant B as bugsy fix participant O as OpenAI participant K as Kane CLI participant A as Ledger participant H as Hack hub U->>B: bugsy fix leak_cross_tenant B->>O: mutant + PRD + tests + evidence O-->>B: "A user must not view another user's invoice" B->>B: write requirements/addendum-leak_cross_tenant.md B->>K: context ingest, review, design tests --max 1 K-->>B: tests/tenant_isolation_test.md B->>A: start BUG=none B->>K: run the new test (authors and records it) K-->>H: passed, verified pass B->>A: restart BUG=leak_cross_tenant B->>K: run the new test K-->>H: failed at "Invoice not found", suspected defect B->>B: commit addendum + test + recordings B->>A: restart BUG=none B->>K: run the suite at the new commit K-->>H: passed, fix re-verified B-->>U: leak_cross_tenant: survived to caught

Two rules. The new test is always authored on the clean app (authoring it on the mutant would record the leak as normal). The requirement must be general, never "invoice #4", so Kane designs a test of the rule, not the seeded row.

Fallback. If Kane's design step pauses twice or passes 3 minutes live, Bugsy prints USING PREPARED TEST and uses the one generated in the morning. Said out loud, never hidden.

Every Kane command runs through kanehack report -- kane-cli …. Exit code decides, a run with no completion event never counts as a pass, and the tree should be committed before runs that matter. Full evidence packs go to the hub, never the public repo; the repo carries redacted exports.

8. What you decide now

  • scope Default matrix is 3 mutants (leak, pay-no-persist, total-off-by-one). Two more are opt-in.
  • credits Only you run Kane against credits. Agents build against recorded output from C1.
  • model Pick OPENAI_MODEL from what your key lists; it goes in .env.
  • honesty The PRD omits tenant isolation on purpose, and we say so. No predicted score in public text.
  • setup In your own terminal: the hub installer, kanehack pair, kanehack consent yes.
